## 1. 决策摘要

### 1.1 一句话

**Mobile App 采用 IM 形态（底部四 Tab + 每 Tab 独立导航栈 + iOS push 语义），定位为 Desktop 的"便携操作终端"而非移植版；Agent 的多会话在移动端以"导航栏标题 = 会话切换器 + Action Sheet"承载（不搬 Session 标签条），并原样消费 ADR-076 的后端 `can_write` 字段实现只读态，不在客户端从 `visibility` 推导写权限。**

### 1.2 关键决策表（详细理由见 §4）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 产品定位 | **Desktop 的功能子集 + 便携终端**，非移植、非远程显示器。两个 App 平级，共享服务端状态，客户端状态各自独立 |
| 2 | 形态 | **IM 风格**（对标企业微信/钉钉），而非 Desktop 三栏布局的窄屏直译 |
| 3 | 底部 Tab | **固定四项**：聊天/项目/文档/设置。**Harness 与 Extensions 不进移动端导航**（设置页保留灰色占位条目） |
| 4 | 导航模型 | **每 Tab 一条独立导航栈 + iOS push 语义**；切 Tab 保留栈深，再点同 Tab 回根 |
| 5 | 二级页 TabBar | **整体滑出隐藏**，避免两级导航并存 |
| 6 | 会话列表 | Desktop 的 AgentList + UserList **合并为单一 IM 会话流**（Agents / 联系人两个分组 + 未读角标） |
| 7 | 会话摘要来源 | **最近活动会话的最后一条消息**，不是 Agent 维度的固定文案 |
| 8 | 多会话承载 | **导航栏标题 = 会话切换器**，点击弹 Action Sheet。**否决**"一个 Agent 一个活动会话"与"Session 标签条" |
| 9 | 会话切换实现 | 必须走 `chatStore.openSession` 等价的**原子迁移**（UI 切换 + `open_session` + HTTP 历史重载），不是本地页面切换 |
| 10 | 只读会话 | **不发 `open_session`**（激活是全局生命周期变更，观众无权开启且无人能负责关闭） |
| 11 | 写权限来源 | **后端 `can_write` 是唯一权威**。禁止从 `visibility` 标签推导；`can_write` 缺失按可写降级 |
| 12 | 只读态 UI | banner + 隐藏审批卡/AskQuestion + **textarea 不渲染** + 可见性图标**禁用而非隐藏** |
| 13 | 新建会话可见性 | 默认落 **Private**，对齐 ADR-076 `create_frontend_session` |
| 14 | 工作区 | **只做 Add to Chat，无文件预览**（无 Monaco；且满足 ADR-009 §5） |
| 15 | 看板 | 窄屏**降级为横向状态 Chip 筛选**，不做拖拽看板 |
| 16 | 本地 Gateway | 移动端**无本地 Gateway 进程** → Desktop 的启停/重启在 v1 禁用；地址配置保留 |
| 17 | 前端代码复用 | **仅复用协议层类型定义**，不共享组件与状态层 |

### 1.3 不变量（必须满足）

1. **权限单一真相**：移动端不产生第二份写权限判定。所有 `can_write === false` 的 UI 禁用都必须能追溯到后端字段，不得由 `visibility`、本地缓存或 UI 猜测产生。
2. **公共可见 ≠ 可写**：一个 🌐 public 会话可以是只读的。任何"公开即能打字"的实现都是 bug。
3. **降级方向是放开而非锁死**：字段缺失、乐观创建、旧 Runtime 省略字段 → 一律按**可写**处理，让后端拒绝；不得因为"答案未知"锁死全部控件。
4. **只读观众不制造生命周期事件**：只读会话不得触发 `open_session` / `close_session`。
5. **多会话是业务事实**：任何"移动端只保留一个活动会话"的设计不予采纳。
6. **TabBar 与返回互斥**：二级页上不存在底部 Tab 与返回按钮两个竞争出口。
7. **工作区只经 Runtime HTTP**：移动端不直连文件系统（ADR-009 §5）。

## 2. 背景与问题

### 2.1 起点：为什么不是"Desktop 的窄屏版"

Desktop App 是开发者工作台：左中右四栏，同时展示导航、Agent 列表、聊天、结果区。它的信息密度假设的是"一个用户、一个房间、一块大屏"。移动端的使用场景完全不同——**站着、走着、随手看一眼**。把四栏压到 390pt 宽，每栏只剩 97pt，得到的是四个都读不清的列。

IM 软件（企业微信/钉钉/微信）之所以成为移动端对话类产品的默认形态，不是因为它"更简洁"，而是因为它匹配了一个具体事实：**人在移动设备上想要的是"和某人说话"，不是"管理一堆面板"**。把这个心智模型搬过来，比缩小 Desktop 更接近用户真实意图。

### 2.2 核心冲突：多会话 vs 屏幕宽度

交互稿初版曾建议"一个 Agent 一个活动会话"，理由是"移动端做 IM 语义，不做 Desktop 的多 Session Tab 并行"。**这个建议被明确否决**：

- **多会话是业务事实**。一个 Agent 同时被多个话题驱动是常态——架构师一边写 ADR、一边 review 别人的 PR、一边调试线上问题。Desktop 用并行 Session Tab 承载。
- **Mobile 只是多个操作终端之一**。用户在 Desktop 上开的会话，手机上要能接着看；手机上新建的会话，Desktop 上要能看到（受权限约束）。砍掉多会话，等于让手机端在功能上不可用。
- **窄屏是"标签条不合适"的理由，不是"多会话不需要"的理由**。这两件事被初版混为一谈了。

于是真正的设计问题变成：**390pt 宽的屏幕用什么容器承载 N 个会话？**

### 2.3 权限的诱惑与陷阱

多用户部署下，session 的可见性有三层语义纠缠在一起：

| 维度 | 取值 | 谁决定 |
|---|---|---|
| 可见性 | public / private | owner（可改） |
| 可读性 | 可读 / 404 | 后端（owner/admin/local 全可读；其他用户仅 public） |
| 可写性 | 可写 / 只读 | 后端（仅 owner/admin/local） |

移动端 UI 上只有一个 🌐/🔒 图标，天然会诱发一个偷懒实现：**"公开 → 能打字，私有 → 不能打字"**。这是错的——public 的会话对其他用户是**只读**的，图标完全相同。ADR-076 §决策 4 已经把 `can_write` 作为独立字段下发，就是为了消灭这个推导；本 ADR 的职责是确保移动端不重新引入它。

---

## 3. 目标

1. 移动端在信息架构上成为**可独立使用的终端**，而非 Desktop 的附属视图。
2. Agent 多会话在移动端**完整可用**（列表/新建/切换/删除/可见性），与 Desktop 共享同一份会话数据。
3. 多用户公开/私有会话的权限语义在移动端**零偏差**，不产生第二份真相。
4. 交互符合主流通 IM 软件的既有习惯，降低学习成本。
5. 首版可交付：范围足够小，能在一个迭代内完成工程搭建与联调。

---

## 4. 决策

### D1：定位为"便携终端"，与 Desktop 平级

Mobile App 不是 Desktop 的远程显示器，不是它的移动版 UI，而是**第二个平级终端**。

两者共享服务端状态（同一批 Agent、同一批 Session、同一套权限），但客户端状态各自独立——Desktop 切走的会话不影响手机，手机新建的会话 Desktop 能看到。

**否决**："Mobile 是 Desktop 的投屏/简化版"。那会让手机端的每一个功能都变成"Desktop 有什么我才能有什么"，与"便携操作终端"的定位冲突。

### D2：底部四 Tab，Harness/Extensions 不进移动端

| Tab | Desktop 对应 |
|-----|--------------|
| 聊天 | AgentList + UserList + ChatPanel |
| 项目 | ProjectsView |
| 文档 | DocsView |
| 设置 | SettingsPage |

Harness 与 Extensions 是**开发者概念**。把它们放进普通用户的底部导航，等于要求用户理解"为什么我的手机上有个我不需要的东西"。设置页以灰色条目 + "仅桌面端"标注保留占位，让功能的存在感与不可用性同时可见。

### D3：每 Tab 独立导航栈 + iOS push 语义

四个 Tab 各自持有一条导航栈：

```
chat:     [会话列表] → [聊天详情]
projects: [项目列表] → [看板] → [任务详情]
docs:     [文档目录] → [文档内容] → [审阅详情]
settings: [设置根页] → [Profile|General|Appearance|Gateway]
```

| 规则 | 行为 |
|------|------|
| 进入二级页 | 底部 TabBar **整体滑出隐藏** |
| 切 Tab | 保留各自栈深 |
| 再点当前 Tab | 回该 Tab 根 |
| 返回 | 逐级 pop，TabBar 随之滑回 |

**为什么二级页隐藏 TabBar**：iOS/微信都不在二级页显示底部栏。若同时显示，用户面对"两个导航出口"（底部 Tab 与右上返回）会困惑。隐藏后只有一条返回路径。

**为什么每 Tab 独立栈**：IM 习惯是"退出会话再回来，还在那个会话"。共用一条栈会导致从项目页回聊天时被迫回到会话列表。

### D4：聊天首页 = 统一会话流

Desktop 的 AgentList 与 UserList 是两个独立面板。移动端合并为**单一 IM 会话流**，分 Agents / 联系人两组。

每行：头像（含在线状态点）、名称、在线状态、**最近会话摘要**、时间、未读角标。

**摘要取自"最近活动会话的最后一条消息"**。这是 IM 语义的必然要求——用户关心的是"上次聊到哪"，不是"这个 Agent 的一句话介绍"。注意这是与会话选择器（§4 D5）联动的：列表摘要与会话选择器展示的是同一个 session，两处必须一致。

### D5：多会话承载 —— 导航栏标题 = 会话切换器

这是本 ADR 的核心决策。

```
┌─────────────────────────────────┐
│  ←      ADR-085 生命周期状态机⌄  ⋯ │  ← 标题 = 会话切换器
│         gpt-5 · 24 条             │     显示 session.title，不是 agent.name
├─────────────────────────────────┤
│              ↓ 点击
├─────────────────────────────────┤
│      架构师 · 会话（8/12）         │
│  已加载最近 8 条，列表可滚动加载更多  │
│  ✓ ADR-085 生命周期状态机评审    🌐  │
│    Relay 模式降级清单        🌐 只读│
│    ADR-084 用户独立进程        🔒  │
├─────────────────────────────────┤
│        ＋ 新建会话                │
│        管理全部会话               │
└─────────────────────────────────┘
```

| 设计点 | 理由 |
|--------|------|
| 标题显示 `session.title` | 用户认的是**话题**，不是机器人。显示 agent.name 会让标题失去信息量 |
| 标题带下拉箭头 | 明确可点，否则用户不知道还有别的会话 |
| 每行 🌐/🔒 | 可见性标记（§4 D7） |
| 只读行"只读"徽章 | 明示不可写，而非让用户发消息失败 |
| ✓ 当前会话 | 位置感 |
| "8/12" + 可滚动 | 对齐 `agentStore.fetchSessions(agentId, page)` 分页 |
| "管理全部会话" | 跳转抽屉的会话分区，做批量管理 |

**为什么不用其他容器**（见 §5 方案对照）。

会话管理（列表/新建/切换/删除/可见性）在抽屉的「会话」分区有完整形态，与 Desktop `SessionPanel` 对齐。新建默认 Private（§4 D8），删除仅对可写会话开放。

### D6：会话切换是原子迁移，不是页面切换

切换会话必须走完整流程（对齐 Desktop `chatStore.openSession`）：

```
点击会话行
    ├─→ ① 前端切换当前 session + 重载消息历史
    ├─→ ② POST /api/agents/{id}/sessions/{sid}/open（ADR-038 激活，幂等）
    └─→ ③ 并行拉取 session config + state
```

**关键认知**：只做 ① 是一个真实存在的错误模式——UI 看起来切了会话，但后端没被告知"这个 session 现在有人在用"，结果是事件流不投递、状态不同步、owner 侧显示该 session 已关闭。Desktop 把这三步合成一个原子操作正是因为它们必须一起发生。

**只读会话跳过 ②**。理由沿用 Desktop `chatStore.openSession` 的注释：激活是 per-session 的**全局**状态，观众若能激活，就制造了一个"自己无权关闭（close 是写授权，刻意不让旁观者拆掉 owner 的会话）、owner 也不知道被谁占着"的常驻会话——生命周期失去责任人。且只读浏览**不需要**激活：历史走 `GET /messages`（读授权），事件流走通配 MQTT 订阅，owner 在用时观众天然能收到。

### D7：写权限消费后端 `can_write`，禁止本地推导

```rust
// core/acowork-runtime/src/conversation.rs
pub struct SessionListView {
    pub session_id: String,
    pub visibility: Option<SessionVisibility>,
    pub can_write: bool,          // ← 唯一权威
}
```

移动端**原样消费**，判定规则与 Desktop `isReadOnlySession` 同构：

```ts
// 只读只在 can_write === false 时成立；缺失按可写处理。
function isReadOnly(canWrite: boolean | undefined): boolean {
  return canWrite === false;
}
```

**为什么缺失按可写**：降级方向必须朝"让后端拒绝"而不是"锁死全部控件"。一个乐观创建、尚未出现在列表里的 session，或一个省略该字段的旧 Runtime，都不该让用户面对一整排死按钮。这条与 Desktop `lib/session-write-access.ts` 的注释完全一致。

| scope \ session | public | private |
|---|---|---|
| admin | 可读可写 | 可读可写 |
| owner | 可读可写 | 可读可写 |
| 其他 user | **可读（只读）** | **不可见**（404） |
| local | 可读可写 | 可读可写 |

**"公共可见 ≠ 可写"是本 ADR 的一条不变量**。一个 🌐 public 会话对其他用户是只读的，图标看起来完全一样。

### D8：只读态的具体 UI 处理

```
┌─────────────────────────────────┐
│ 🔒 只读 · 来自 Alice 的共享会话，你不能发送消息 │  ← banner
├─────────────────────────────────┤
│           （消息列表，只读）        │
├─────────────────────────────────┤
│ 🔒 共享自 Alice · 只读            │  ← 替换掉 textarea
└─────────────────────────────────┘
```

| 控件 | 只读时 | 理由 |
|------|--------|------|
| textarea | **不渲染** | placeholder 假装可输入，比明确禁用更糟 |
| 发送/工具/附件 | 不渲染 | 无写入路径 |
| 审批卡 / AskQuestion | **隐藏** | 它们让观众替 owner 做决定 |
| 可见性图标 | **禁用，不隐藏** | 观众仍需知道自己在看一个私有会话 |
| 改可见性 / 删除 | 菜单项 disabled + 原因副标题 | 不做成"点了才 toast" |

**可见性图标禁用而非隐藏**沿用 Desktop `SessionVisibilityToggle` 的既有规则——该组件的注释明确说明：观众若连图标都看不到，就不知道自己看的是什么，"那个开关就会显示'公开'给一个谁都读不到的会话"。

### D9：新建会话默认 Private

对齐 ADR-076 的 `create_frontend_session`——创建路径在写入 `user_id` 的同时落 `Some(Private)`，**写死在盘上不靠读路径推断**。移动端前端就按 private 提交，避免"新建即公开、bob 可读"的窗口。

### D10：工作区只做 Add to Chat

移动端没有 Monaco，**不做文件预览**。文件树保留，Add to Chat 保留，文件内容由 Agent 在对话中读取。

这同时满足 [ADR-009 §5](./ADR-009-gateway-workspace-isolation.md) 的 Gateway 工作区隔离——移动端不直连文件系统，只经 Gateway 反代走 Runtime HTTP。

### D11：窄屏功能降级而非伪造

| 功能 | 降级方式 |
|------|---------|
| 看板 | 横向状态 Chip 筛选，**不做拖拽看板**（窄屏拖拽不可用） |
| 代码块 | 横向滚动，**不做语法高亮**（无 Monaco） |
| 工具调用 | 折叠卡片，默认收起 |
| 本地 Gateway 启停 | **禁用**（移动端无此进程），地址配置保留 |

原则：**降级要诚实**。做一个不能用的迷你拖拽看板，比明说"请在桌面端操作"更糟。

### D12：不共享 Desktop 前端代码库

移动端与 Desktop 共享**协议层类型定义**（`SessionInfo`、`can_write` 语义），但**不共享组件与状态层**。

两者的信息架构、组件集、交互范式完全不同。强行共享一套代码库会积累大量 `isMobile` 条件分支，最终比写两套更难维护。

## 5. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| **A. 一个 Agent 一个活动会话** | **用户明确否决**。多会话是业务事实，Mobile 是多个操作终端之一；不支持多会话功能上不可用。窄屏是"标签条不合适"的理由，不是"多会话不需要"的理由（§2.2） |
| **B. 搬 Desktop 的 SessionTabBar 标签条** | 390pt 宽放不下 N 个并排标签（每个至少 80pt，5 个会话就溢出）；且标签条是"编辑器"心智，与 IM 不符 |
| **C. 会话做成底部横向滑动卡片（Pager）** | 横向手势与"右滑返回"冲突——用户在消息区右滑到底是翻页还是返回？这是手势语义的灾难区。IM 从不用这种方式承载会话 |
| **D. 会话列表做成聊天页顶部的下拉面板** | 顶部下拉与右滑返回在起点区域冲突；且会话数一多就需要二级页，绕回原问题 |
| **E. 从 `visibility` 推导可写性** | **危险**。public 对其他用户是只读的，图标相同，推导必然产生错误授权。ADR-076 独立下发 `can_write` 正是为此（§2.3） |
| **F. 字段缺失时按只读处理** | 降级方向错误。一个乐观创建的 session 或旧 Runtime 省略字段会让全部控件失效，用户无法发送任何消息。应当"放开让后端拒绝"（D7） |
| **G. 只读会话也发 `open_session`** | 制造"观众无权关闭、owner 不知道被谁占着"的常驻会话，生命周期失去责任人（ADR-076 §决策 4 的原话） |
| **H. 隐藏可见性图标而非禁用** | 观众失去"我在看私有内容"的信息。Desktop `SessionVisibilityToggle` 明确选择了"禁用而非隐藏" |
| **I. 只读时用 placeholder 提示"无法发送"** | placeholder 看起来可输入，用户会反复尝试。明确不渲染 textarea 诚实得多 |
| **J. 共享 Desktop 前端代码库** | IA/组件/交互范式完全不同，共享会积累大量条件分支（D12） |
| **K. 移动端也做本地 Gateway 管理** | 移动端不存在这个进程。启停控制是纯粹的伪功能 |
| **L. 移动端做完整功能平移（含 DevMode/Git/Agent 创建）** | v1 范围失控，且这些功能依赖本地文件系统/进程控制/大屏，与"便携终端"定位冲突 |

## 6. 后果

### 6.1 正面

- 移动端成为可独立使用的终端，具备完整多会话能力。
- 权限语义与后端零偏差，消除了"从公开推导可写"这一类错误授权。
- 交互符合主流 IM 习惯，用户学习成本低。
- 首版范围明确（4 Tab、无调试、无管理操作），可在一个迭代内交付。
- 只读态的每个 UI 决策都有 Desktop 先例（`SessionVisibilityToggle` / `session-write-access.ts`），不是凭空发明。

### 6.2 负面 / 成本

- **协议层类型需要跨仓库共享**：移动端要复用 `SessionInfo` / `can_write` 语义，需要抽出一个共享类型 crate 或包，否则会漂移。
- **两套状态层**：Desktop 与 Mobile 各有一套 store，多会话逻辑需要实现两次（`fetchSessions` 分页、`openSession` 原子迁移、`can_write` 判定）。这是 D12 的直接代价。
- **组件需重建**：inset 列表、Switch、Segmented、Stepper、Action Sheet 在 Desktop 无对应物，需新建移动端组件集。
- **手势冲突面变大**：左滑抽屉 / 右滑返回 / 垂直滚动 / 横向子列表四者共存，是原型验证中 bug 最集中的区域。
- 多会话 UI 在窄屏下的信息密度需要持续调优（当前 8 条/屏）。

### 6.3 边界 / 例外

- **用户-用户聊天没有会话概念**：它由 Gateway 侧以规范化 pair id（`min__max`）存储，是 1:1 的，**不进入会话切换器**。只有 Agent 对话有多会话。
- **local 模式**：`can_write` 恒为 true，权限相关 UI 全部隐藏即可，逻辑不变。
- **只有一个会话的 Agent**：会话切换器仍显示（点开只有一条 + 新建），不特殊处理——保持交互可预测。
- **无会话的 Agent**（如已停止的文档管理员）：展示"暂无会话"，新建入口保留。

### 6.4 回滚

本 ADR 全部是客户端决策，不改变任何协议、后端或数据结构。回滚 = 回退移动端应用版本，Desktop 侧零影响。这是刻意的：把信息架构决策限制在客户端，使得这个决策错了也**不产生需要清理的迁移**。

### 6.5 验证记录

交互原型 [`docs/prototypes/mobile-im-v1.html`](../../prototypes/mobile-im-v1.html) 经双层自动化验证：

| 层 | 工具 | 用例 | 结果 |
|----|------|------|------|
| 行为 | jsdom（真实点击 + 合成 touch 事件） | 60 | 60 通过 |
| 布局 | WKWebView 实测 `getBoundingClientRect` | 44 | 44 通过 |

布局层不可省略：jsdom 对所有几何值返回 0，会掩盖真实溢出。实测暴露的 4 个真实缺陷（导航栏副标题因 DOM 层级错误从未渲染、会话切换器撑破导航栏 grid 列、会话列表因 `max-height:46vh` 过高而永不滚动、会话名在 Action Sheet 中重复渲染）全部是纯客户端问题，符合 §6.4 的回滚预期。

### 6.6 已知技术债 / 后续

- 移动端与 Desktop 的多会话逻辑重复实现。建议在协议层之上抽一个**纯函数共享包**（`isReadOnlySession` / 会话排序 / 摘要提取），但不强行共享状态层。
- 移动端 App Extension（iOS）未评估。
- 文档协同编辑（ADR-079 Yjs）在移动端的形态未评估——预计 v2 之后。
- 移动端的推送通知（Agent 完成时提醒）未纳入 v1。
