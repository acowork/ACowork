## 1. 决策摘要

### 1.1 一句话

**在「字节隧道」之外新增第二种远程访问模式 Cloud Hub——一个理解消息语义的有状态后端服务**：
Gateway 侧只发出站短 HTTPS 请求（长轮询取命令 + POST 上报带 `seq` 的事件），
Desktop / Mobile 侧走标准 REST + SSE，两侧在**命令/事件语义层**相遇而非 TCP 字节层。
**与 24 号瘦中继永久并存、用户自选**，不是替代：Relay = 自带 VPS 的自托管 BYO 档（我方零云成本、零合规暴露、中继零秘密），
Hub = 默认托管档（离线消息、跨设备同步、推送、审计）。
并存的前提是**四条硬约束 P1–P4**（单一能力清单、单一设备身份、客户端单一抽象、传输无关一致性测试）
与 **Relay 协议冻结在 `proto=1`**（此后只接安全修复）。

### 1.2 关键决策表

| # | 决策 | 结论 |
|---|---|---|
| 1 | 中继抽象层级 | 从「协议无关字节管道」改为「应用层消息（命令 + 事件）」——**新增一种，不替换** |
| 2 | 真相源 | **Gateway 仍是唯一权威**。Hub 只持有两类有界非权威数据：TTL 有界的投递缓冲、带 `source_version` 的投影缓存 |
| 3 | 远程 MQTT | **Hub 模式下完全移除**（无 `:19874` 远程 listener、无 `/mqtt` WS→TCP 桥、无按来源 ACL）；Relay 模式保留（冻结） |
| 4 | 能力面定义 | **单一 `RemoteSurfaceManifest`**（实测 32 个路径模板 → 约 30 op + 6 stream；且远程面横跨 4 个服务，经 Gateway 回环代理复用既有链路），**同时生成 Hub 注册表与 Relay 白名单**，CI 漂移检查锁定 |
| 5 | 身份分层 | Hub 层认证「你是谁 / 设备是否已配对」；Gateway 层裁决「你能不能做」。Hub 对授权**不可信** |
| 6 | 命令防伪 | 客户端 **Ed25519 端到端签名**，公钥登记在 Gateway；Hub 被攻破也无法对 Gateway 下达有效命令 |
| 7 | 内容机密性 | 托管形态默认 **E2E 信封加密**（Hub 只存密文）；自托管允许显式关闭 |
| 8 | 下行承载 | **SSE + 长轮询 fallback，不用 WebSocket**；上行短命 POST；Gateway 取命令用长轮询（保持仅出站不变式） |
| 9 | 流式输出 | 事件批合并（时间/条数双阈值），**不代理 SSE 原流** |
| 10 | Relay 演进 | **冻结**：取消原计划的 QUIC 承载与多实例 Redis 分流；通配符子域与 SNI 路由保持原样 |
| 11 | 开源/闭源边界 | 协议与单租户参考实现在开源仓；多租户 / 计费 / 厂商推送 / 地域准入 / 境内部署在闭源仓 |

## 2. 背景与问题

24 号瘦中继落地过程中暴露两个**同一根因**的问题：

1. **网络维度**：隧道是长寿命、多路复用、非标准指纹的连接（WSS + yamux + 通配符设备子域 SNI 路由）。
   在受限网络环境中这类连接最易被识别与中断；一旦被中断，**yamux 上所有复用流同时死亡**，
   且隧道不持有状态，**没有任何恢复点**。
2. **商业维度**：字节管道**没有产品面**。离线消息、跨设备未读同步、推送、审计、按用量计费——
   全部要求中继理解语义，而「按设计不理解语义」正是 24 的核心优点。二者不可调和。

同时，24 的技术内核（单真相源、Broker 留在 Gateway、中继零秘密）是**正确的**，不应被推翻。

## 3. 备选方案

| 方案 | 结论 | 否决/采纳理由 |
|---|---|---|
| **A. Cloud Hub 应用层中枢，与 Relay 并存** | ✅ **采纳** | 可恢复性来自消息级游标；商业化能力长在这一层；顺带消除远程 MQTT 四块最复杂代码；Relay 的 BYO 优势得以保留 |
| A′. Hub 替换并删除 Relay | ❌ 否决（用户定案） | Relay 的「我方零云成本 + 零合规暴露 + 中继零秘密」是 Hub **永远拿不到**的商业优势；删除即丢掉隐私优先与自带 VPS 人群 |
| B. 只加固隧道（境内 VPS / QUIC / CDN 前置） | ❌ 否决作为终态 | 长寿命多路复用 + 通配符子域仍是最易识别指纹；**加固投入无法回收**（无商业化产品面） |
| C. 云端成为会话真相源（Gateway 反向同步） | ❌ **明确否决** | 双真相源，与 24 §3.2 否决「公网 Broker + Bridge」**完全同构**的理由：会话语义被切断、控制面双写、离线语义反转 |
| D. 纯推送 + 轮询 | ❌ 否决为主通道 | 工具审批 / 提问等交互延迟不可接受；**保留为 A 内部辅助信道**（推送只叫醒，不传内容） |

## 4. 决策理由

### 4.1 为什么「并存」优于「替换」

两种模式服务**互不重叠**的人群与约束：

| | Relay（24） | Cloud Hub（26） |
|---|---|---|
| 谁运营 | 用户自带 VPS | 官方托管 / 企业自托管 |
| 我方云成本 | **零** | 承担存储与带宽 |
| 合规暴露 | 我方不持有流量 | 我方是服务提供方 |
| 受限网络可用性 | ⚠️ 差 | ✅ 好 |
| 独有能力 | 任意协议透传（新协议零改造） | 离线消息、跨设备同步、推送、审计 |

**关键判断**：Relay 不是历史包袱，它是 **BYO 档**。删掉它等于把最不需要我方基础设施、
合规风险最低的一群用户推向竞争对手。

### 4.2 为什么并存必须受约束（P1–P4）

并存的最大风险不是成本，而是**同一远程能力的两份实现、两份安全模型、两份 bug**。四条约束各自封堵一条退化路径：

| 约束 | 封堵的退化 |
|---|---|
| **P1 单一 Manifest** | 能力漂移（用户切模式即功能缺失）+ Relay 控制面暴露风险永久化 |
| **P2 单一设备身份** | 两套凭据 → 撤销漏一侧 → 已撤销设备仍可访问 |
| **P3 单一 `RemoteClient` 抽象** | 业务代码按模式分支 → 每个功能写两遍 → god-module |
| **P4 传输无关一致性测试** | 行为漂移无人发现（**唯一能证明并存没腐化的机制**） |

**P1 是本次决策中最重要的新增工作**：它要求 Relay 补一道白名单闸门（现在它按设计是任意字节透传）。
这不是重构隧道，而是在 Gateway `remote_listener` 上加路径/topic 允许列表——
恰好把 24 §3.2 第 3 条「一条 topic 过滤规则配错即公网暴露控制面」从**「靠配置正确」升级为「靠构造不可能」**。
**并存反而让 Relay 更安全**，这是替换方案拿不到的收益。

### 4.3 为什么 Hub 必须理解语义，而授权仍在两端

Hub 理解**路由 / 排队 / 计量**（这是商业化与可恢复性的来源），但**不理解授权**：

- 命令由客户端 Ed25519 私钥端到端签名，公钥登记在 Gateway，Gateway 本地验签 + 本地 ACL 裁决后才执行。
- **后果**：Hub 被完全攻破 → 攻击者能读密文（若 E2E 开启则连密文也读不懂内容）、能丢弃/重放命令，
  但**无法对 Gateway 下达任何有效新命令**。
- 这是对 24 OQ-7「中继不验证用户 token」立场的推广：**把「中继零秘密」的原则升级为「中枢零授权」**。

### 4.4 为什么 Relay 要冻结

一个**冻结**的第二模式维护成本接近零；一个**持续演进**的第二模式会不断与新模式抢协议设计话语权，
最终变成两个都不完整。因此取消 24 原计划中的 QUIC 承载演进与多实例 Redis 分流。
冻结**不等于**放弃 P1——Relay 仍需一次性补齐白名单闸门。

## 5. 后果

### 5.1 正面

- 远程访问在受限网络下具备**明确恢复点**（游标续传），而非全流死亡后重建
- 离线消息、跨设备同步、推送、审计、计量成为可能 → 商业化产品面成立
- Hub 模式下远程 MQTT 四块复杂代码不再被使用；控制面暴露从构造上消除（**两种模式都受益**）
- 破解 24 v0.2.1 的「隧道必须先于登录可用」鸡生蛋死锁（Hub 模式登录可在 Hub 完成，配对后才建立会话）
- 合规阻塞项**降级**：境内用户可先用「自建 VPS + Relay」获得远程访问，我方零合规暴露；
  Hub 的境内/境外拓扑决策可推迟，不阻塞 Phase 0–2 工程

### 5.2 负面与代价（必须承认）

- **Hub 不再协议无关**：每个远程能力都要显式声明并测试。这是本决策唯一真正的复杂度来源
- 命令经 Hub 增加 2 跳，交互延迟上升（目标 p50 < 300 ms，需实测）
- 流式输出需批合并，首字延迟 +150–250 ms
- E2E 加密使 Hub 侧无内容检索、无推送预览
- **两种模式的长期维护成本**：即使冻结，Relay 仍需安全修复与 P4 双传输测试门禁
- 客户端需实现两套 transport（由 P3 抽象层约束其影响面）

### 5.3 风险与前置验证

| 风险 | 缓解 |
|---|---|
| **A1：SSE 经真实反向代理/CDN 被缓冲**（H2 成立前提） | Phase 0 第一验证项；协议设计上长轮询**语义等价**，仅延迟不同 → 风险不致命 |
| 游标续传做不到「不丢不重」 | **Phase 1 混沌测试为方案成立判据**：随机在任意字节偏移切断连接。若失败，**立即停止投资 Phase 2+** |
| 并存腐化（P1/P4 失守） | CI 漂移检查 + 双传输一致性测试作为**必跑门禁** |
| 投影被当权威（静默错误状态） | 强制 `source_version` + UI 显式陈旧标注（禁止 silent fallback） |

## 6. 实施边界

| 归属 | 内容 |
|---|---|
| **开源仓**（本 ADR / 设计 26） | `acowork-core::hub` wire format（**唯一**定义处）、单租户可自托管 Hub 参考实现、Gateway `hub-connector`、客户端 `RemoteClient` 抽象与 Hub transport、`RemoteSurfaceManifest` + CI 漂移检查 + Relay 白名单生成、E2E 信封加密机制、配对与设备签名验证、Relay 冻结 |
| **闭源仓**（Hub 多租户 SaaS 实现层文档，不随本仓分发） | 多租户数据模型（`tenant_id` 判别列、Postgres/Redis 分层）、订阅与计量计费、地域准入与 geo-fencing、国内厂商推送通道、管理控制台与审计导出、SLA、跨租户互通、境内云部署与 ICP 备案主体决策 |

**硬规则沿用** C1–C4：闭源仓依赖开源 `acowork-core` crate，**禁止 fork**；协议变更单向流动
（闭源提议 → 开源发布 → 闭源跟随）；商业能力只存在于实现层，协议层 `caps` 只声明不消费。

## 7. 回滚策略

- Gateway 配置 `remote.transport = relay | hub | off`（复用 F11 已有的运行时开关形态），
  **逐 Gateway 灰度**，Hub 出问题一行开关回切 Relay，Relay 代码不动。
- 开源 Hub 与 Relay 为**并列模块**（`src/hub/` vs `src/relay/`），互斥运行，仅共享身份与 ACL 裁决层；
  任何一方出问题不需要回滚另一方。
- 投影与 E2E 为 Phase 3 增量，可独立关闭（E2E 关闭需**显式配置**，禁止静默降级）。
